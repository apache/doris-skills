# 5. Keep the evidence tied to the final candidate

- Keep the baseline and the candidate apart. With uncommitted changes, `HEAD` alone doesn't represent the candidate; identify it by the actual diff or the state of the relevant files.
- When builds or images are involved, confirm where the binaries that ran came from; don't credit the new code with results from an old binary or a stale cache. Record a build ID, an image digest, or the source of an executable only when needed, to make sure that what was tested is the candidate's build.
- When the code, related dependencies, test inputs, or build configs change after the self-review, re-verify the conclusions they affect. When you find that the baseline, the related source, dependencies, test inputs, or build configs have changed, work out which existing conclusions are affected and rerun those checks. There is no need to rerun checks that truly aren't affected; an unrelated wording change doesn't call for redoing all the verification.
- After committing the code as the project or the user requires: when the commit matches the working tree the evidence was gathered on, record that commit as the evidence's code version; when it doesn't, re-verify the affected conclusions. Only committed changes go into the PR. When the project wants commit messages to follow the PR template (as Doris does), write the commit message from the draft in the handoff file.
- After a rebase, the commit the evidence was gathered on is no longer in the branch history. Use `git diff <the commit the evidence ran on> HEAD -- <paths of the tested code and its tests>` to tell whether they changed: where nothing changed, record the new commit as the code version; where something changed, upstream changes included, verify again.
- When the task is interrupted, keep in the handoff file what resuming needs: the current stage, the code in question, the evidence so far, the open problems, and the next step. Check them again after resuming; results that have gone stale cannot count as passes.
- Mark each evidence entry clearly as `VERIFIED`, `FAILED`, `NOT_RUN`, or `NOT_APPLICABLE`. State execution results, static inferences, and unverified assumptions separately. Mark stale evidence `NOT_RUN` with the reason, rather than deleting it.
