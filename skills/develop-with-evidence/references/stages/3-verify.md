# 3. Run verification that tells right from wrong

Follow the change-type strategy chosen in stage 1, and record the commands or steps, the expectations, and the actual observations that help someone check the work again. Before recording evidence for the first time, read `references/evidence-entry.md`, and write the entries into the handoff file in its format.

- For a bug that can be reproduced reliably at a reasonable cost, show that the same regression test fails on the baseline because of the target defect and passes on the candidate. An environment failure or a build failure is not a valid reproduction. New features and refactors don't have to manufacture a baseline failure.
- Take expectations from the requirement, an existing contract, a protocol, or an independent reference. Don't copy the implementation's logic into the test and then treat it as proof of correctness. When the framework generates the expected results from the implementation's output (snapshots or golden files, such as the `.out` files of Doris regression tests), check each generated item against an independent expectation; for a defect fix, confirm that the baseline code produces different output at the target spot.
- Confirm that the tests really ran, the target path was reached, and the assertions can tell right from wrong. Watch for zero cases, everything skipped, loops over empty collections, swallowed exceptions, broken fixtures, mocks that hide the logic under test, and checks of names rather than behavior. For a new or changed test, also confirm that the project's CI will run it: check the test groups, the exclude lists, and the run switches. If it won't run, move it to where it will, or say so in the handoff file. When the project's PR description skill says how to check this, follow it, such as doris-pr-description's `references/facts/existing-tests.md`.
- When changing code, find the existing tests closest to the change, one layer each for unit tests and end-to-end tests, and the tests that assert the changed behavior (generated expected-result files included), and check whether this change updates them. Write the results into `Existing tests` in the handoff file, so that the PR step doesn't look them up again.
- When you suspect that a test could pass falsely, use a minimal input known to be wrong, a targeted revert of the fix, or a mutation. Prefer an isolated copy or working tree; keep the developer's uncommitted changes, and afterward restore the code and check the final diff to confirm that no deliberate breakage, test bypass, or debug switch is left behind. Never use a destructive reset to set up the baseline. Don't run full mutation testing by default.
- Verify the related paths, boundaries, invalid inputs, state transitions, and compatibility as the actual risk calls for. For performance, measure both the target workload and a plausible unfavorable one, and disclose regressions and noise.
- When changing tests or CI detection logic, show that they still catch the errors they promise to detect. For an intermittent failure, control the trigger condition first, rather than rerunning until it turns green.
- When a required environment is unavailable, continue with the work that can be done, and list the missing checks as unverified; never invent command results, independent reviews, or coverage. `references/evidence-entry.md` says how to deliver when blocked.

Building, deploying, and running tests, as well as finding the existing tests and checking CI coverage, can all go to subagents, with the main session receiving only the conclusions and the log locations; see `references/subagents.md`. Targeted reverts and mutations change code in the working tree, so they stay in the main session.
