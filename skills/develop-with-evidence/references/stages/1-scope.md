# 1. Define the goal, the scope, and how much to verify

1. Read the requirement, the existing discussion, the project's conventions, and the relevant code; check the current diff and any existing fixes. First confirm that the problem to solve still exists.
2. When the change fixes a bug, first confirm that the bug is real and try to reproduce it, then continue with this stage. A bug report can be wrong: the symptom may come from an old version or a wrong config, the expectation itself may be wrong, or the cause may be only a guess. Treat the symptom, the trigger, and the cause in the report as claims to verify, and when you describe the current behavior later, go by what you observed.
   - **Reproduce:** on the unmodified code (the baseline), follow the report's input and steps, as `references/change-types/bugfix.md` describes. When the reproduction can be written as a regression test, write it as one right away: its result on the baseline is the baseline evidence that stage 3 needs. When the bug can't be reproduced, trace the causal chain from the input to the wrong result through the source, the logs, or the stack trace.
   - **The defect is real:** it reproduced or the causal chain holds, and the result contradicts the requirement, the documentation, or an existing contract, not just the reporter's expectation. Record in the handoff file where the report and the observations differ (the symptom, the trigger, the scope of impact, or the cause), and point it out to the developer at delivery. When it did not reproduce, record the limits of the reproduction.
   - **Proven not to exist:** this needs positive evidence, such as the reported behavior matching the documentation or the contract, the baseline already having the fix (find the commit that fixed it), the reported trigger being impossible in the code, or the symptom coming from something outside the code, such as the config or the environment. Failing to reproduce it is not enough. Stop developing, tell the developer what you checked, the evidence (commands and output, `path:line`, the source of the contract, or the commit), and the conclusion, and ask for their view. If the developer still wants to change behavior that matches the contract, treat it as an enhancement of an existing feature.
   - **Cannot tell:** it neither reproduced nor yields a causal chain. Don't conclude from this that it doesn't exist, and don't fix it on a guess. Stop developing here too: explain what you tried and what was missing (the environment, data, version, or logs), and ask the developer to supply it or to decide whether to continue.
3. When the repository has a PR template (such as `.github/PULL_REQUEST_TEMPLATE.md`), or the environment has the project's PR description skill (such as `doris-pr-description` for Doris), read the part of it meant for development: determine the PR type by its type table, add that type's required information and what reviewers check to the acceptance goals, and leave evidence for the development-stage items it lists. In doris-pr-description, the part meant for development is its `references/development.md`, which points to the type table, the current type's file, and how to look up specific facts; you don't need to read the skill's other files. When there is a handoff file, the PR step takes its facts as given and doesn't collect them again, so everything the PR description skill lists for the handoff (for doris-pr-description, its `references/development.md`) must be established during development. The verification strategy is still chosen by this skill's change types.
4. Settle, in a short description: the expected behavior, the current behavior, the inputs or states it applies to, the contracts that must hold, the boundary of the change, and the observable acceptance results. For a new feature, write the target contract; for a refactor, write the behavior that stays the same, and don't invent a "failure".
5. Keep known facts, reasonable assumptions, and open questions apart. Make the usual implementation choices yourself and state the assumptions they need; don't take a guess for the root cause. When a user-visible contract is involved (syntax, names, defaults, configs, privileges), write the chosen approach, the alternatives rejected, and the reasons into the handoff file; the PR step writes the design notes from them, and drafts the issue from them when one is needed.
6. Choose the smallest set of verification that works, by change type and risk. Read the quick reference in `references/change-types/index.md` first, then only the strategy file of the type you chose; when one change spans several types, read only the extra files for the risks they add.
   - Low-impact wording, comments, pure formatting: check the diff and, where needed, the rendering or the syntax; usually no new tests are needed.
   - Behavior changes: cover the main promises and the directly affected paths, reusing the related tests.
   - Privileges, persistence, concurrency, protocols or formats, or critical performance paths: add boundary, failure, and compatibility checks aimed at this change's risks, and run the checks that the project explicitly requires.
7. Before implementing, settle where the main expectations come from and which observations will show success. Write a short plan or an evidence record only when it really helps, and don't create extra files for small tasks. The handoff file is the exception: it lives inside the `.git` directory, and a few lines are enough for a light task.
8. Read `references/handoff.md`, create the handoff file, and write this stage's goal and decisions into it. For a bug, record the reproduction or the causal chain that confirmed the defect as evidence, in the format of `references/evidence-entry.md`.

The building, deploying, and running that the reproduction in item 2 needs can go to a subagent, with the main session receiving only the conclusions and the log locations; the main session decides whether the defect is real. See `references/subagents.md`.
