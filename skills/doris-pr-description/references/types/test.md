# Test

Title tag: `test`. Use when only test code or test infrastructure changes: regression suites and their `.out` files, unit tests, docker test environments, test frameworks. If production code changes too, classify the PR by the production change; a flaky test caused by a real race in production code is a Bugfix.

Test PRs come in two kinds with different fields: adding or extending tests, and fixing an existing test.

## What reviewers check

- What does this test catch that existing tests don't?
- Would it fail if the logic it tests broke? A test that passes either way is the most common complaint on Test PRs.
- For a fix: is the flakiness really gone, or only rarer?

## Background

What the tested feature does. For a fix, also what the test checks, and where and how it runs: its pipeline, its environment, the services it needs.

## Problem Summary

When adding tests: the risk or regression they guard against, and the bug or feature they relate to. When fixing a test: which test, how it fails, and the fix in one sentence.

## Details for adding or extending tests

- **Scenarios** (required): the cases covered, such as the normal path, boundaries, negative cases, error codes, concurrency, restarts, and failure recovery, whichever apply.
- **What existing tests miss** (required): what these tests cover that existing tests don't, naming the closest existing suite.
- **Fails when broken** (required): evidence that the test catches the problem: it fails when the tested logic is reverted or broken (say how you checked), or it reproduces the original bug.

## Details for fixing an existing test

- **Failure** (required): how the test fails (the error text, a CI run) and how often.
- **Cause** (required): why it fails: timing, ordering, shared state, the environment, a wrong expectation, or a change made in another PR.
- **Stability evidence** (required): how you know it is fixed, for example 50 consecutive local runs without a failure, or the failing CI job passing repeatedly.

## Conditional fields for both kinds

- **External dependencies** (when the test needs external services): the docker images, versions, accounts, and network requirements.
- **Removed tests** (when tests are deleted): why, what replaces their coverage, and whether CI still references them.

## Testing

How the new or changed tests were run, and where. Regression output files must be generated by the framework rather than written by hand (see `AGENTS.md`); there is no need to say so in the description.

## Establish during development

What only development can establish, for the handoff file (`references/development.md`):

- Adding tests: that each new test fails when the logic it tests is broken or reverted, and how you broke it.
- Fixing a test: the failure rate before and after, from the same number of runs, or a run that forces the timing that caused the failure.
- That a PR pipeline runs the test (`references/facts/existing-tests.md`).
