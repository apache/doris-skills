# Case-001: Queries Still Read Fully from S3 After Warmup — FE Dispatches Empty Batches

## Environment

- Doris version: 4.0.4.9 (cloud)
- Architecture: storage-compute separation, 3 BE in compute group `batch_data`

## Symptom

After running `WARM UP TABLE ods.ods_event_ri`, `SHOW WARM UP JOB` shows all 91 jobs as `FINISHED` with `AllBatch=0`, completing in only a few seconds. But subsequent queries still read fully from S3, with 0% local file_cache hit rate.

The user repeatedly ran warmup and `force` warmup with the same result.

## Key evidence

### FE logs

```
send warm up request. job_id=..., batch_id=0, job_sizes=0, request_type=SET_JOB
```
273 occurrences in total (91 jobs × 3 BEs), all with `job_sizes=0`.

FE computed a non-zero warm-up size (about 0.2~0.5GB per job), but the batches dispatched to BEs were empty.

### BE logs

```
SET_BATCH ... jobs size=0
pending_job_size=0|finish_job_size=0
CLEAR_JOB
```

Every time: `jobs size=0` → status query returns pending=0 → immediately `CLEAR_JOB`.

The BE logs contain no actual download/warmup keywords such as `download_segment_file`, `warm_up_cache_async`, or `FileCacheBlockDownloader`.

## Investigation

### Step 1: Confirm warmup job status

`SHOW WARM UP JOB` shows `FINISHED` + `AllBatch=0`. Download failure is ruled out — downloads were never triggered at all.

### Step 2: Code path verification (4.0.4.9)

```
CacheHotspotManager.warmUpNewClusterByTable()
  1. Accumulate partition.getDataSize(true) per partition
     → prints a non-zero warm up size
  2. Intersect the partition's tablets with
     CloudTabletRebalancer.getSnapshotTabletsInPrimaryByBeId()
     → only tablets present in that BE's primary snapshot are added
       to beToWarmUpTablets
  3. splitBatch() on an empty tablet list → empty batch
  4. CloudWarmUpJob.buildJobMetas() with an empty batch → empty job_metas
  5. BE CloudBackendService::warm_up_tablets() receives empty job_metas
     → no pending tasks
  6. FE sees pending=0 → marks the job FINISHED and cleans it up
```

### Step 3: Root cause confirmation

The FE route/rebalancer snapshot has no mapping of the target partition's tablets to these 3 BEs.
Possible causes: the route snapshot was just initialized, BEs were replaced/scaled and the snapshot has not stabilized, or the snapshot is inconsistent with the actual query routing.

## Root Cause

It is not a BE download failure — the per-BE warm-up tablet batches generated by FE are empty. The reason is that the cloud tablet rebalancer snapshot contains no mapping from the target table partition's tablets to the target BEs.

The `force` parameter cannot fix this (in 4.0.4.9 code, `force` only bypasses the cache capacity check; it does not repair empty tablet mappings).

## Fix

- **Verify the route snapshot**: Before rerunning warmup, confirm that `CloudTabletRebalancer.getSnapshotTabletsInPrimaryByBeId` returns non-empty results for the target BEs and includes the target table partition's tablets
- **Wait for routes to stabilize**: If the cluster was just scaled, wait for the cloud tablet rebalancer to complete a round of stable routing before running warmup
- **Verify via FE/BE logs**: On rerun, confirm `job_sizes > 0`, and in BE logs that `jobs size > 0` and `pending_job_size` was once non-zero
- **Code improvement**: When `warm up size > 0` but all BE batches are empty, the job should not return `FINISHED`; it should fail/cancel and report that the route snapshot has no target tablets

## Key diagnostic actions

1. `SHOW WARM UP JOB` check `AllBatch` — if it is 0, the problem is not in downloading
2. Search FE logs for `send warm up request` → confirm whether `job_sizes` is 0
3. Search BE logs for `SET_BATCH` → confirm whether `jobs size` is 0
4. Search BE logs for `download_segment_file` → if entirely absent, downloads were never triggered
5. Check the `CloudTabletRebalancer` snapshot state
